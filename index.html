Finding a few constants

A person on the 3DBrew Wiki by the alias of "turdsucker" posted the following image online of a python program to decode the 3DS gamecard protocol:


Unfortunately, a bunch of constants are blurred out. I have written this "essay", or whatever you want to call it, as the first and only published attempt at finding all of these constants to piece together the 3DS protocol. I also want this to be a teaching resource, so that people can see that reverse engineering can be very fulfilling and interesting, but also extremely difficult. I have been working on all of this for almost a year now. Even though what I write seems super straightforward and easy, I actually went through a lot of trouble and dead ends here. People don't usually show the hard part, which is fine, but also makes it seem like oneself is worse than they actually are. Just remember that what seems like a dead end may actually not be if you have faith that it will work.

The Easy Part

It is luckily very easy to figure out what the titlekey1 and 2 variables are. They are equal to the AES CCM plaintext extracted from a 3DS gamecard's unencrypted header when decrypted from a derived normalkey. What does this mean? It means that to decode, use the following steps:

  1. Take the KeyY from your gamecard, and derive a normalkey using the following: NormalKey = ((((0xB529221CDDB5DB5A1BF26EFF2041E875 <<< 2) ^ KeyY) + 1FF9E9AAC5FE0408024591DC5D52768A) >>> 87)
    This gives a NormalKey of 0xEC6F2D0C307A113A8F1E6AB6B83907A6
  2. Take the NormalKey, and then use it in an AES-CCM cipher as follows:
    • NormalKey: 0xEC6F2D0C307A113A8F1E6AB6B83907A6
    • Nonce: 0x9159D7383348DF83FD71842C
    • MAC: 0x8E6B272F0801283BD430DE4437F5B046
    • Ciphertext:0xB3CFFBC66AB1CB2032AFCE35D41C74C9

This gives a result of 0x417BC9A2F53D9EEFDF58CF9916C8DD13, meaning that the titlekey variables are as follows:
titlekey1 = 0x417BC9A2F53D9EEF
titlekey2 = 0xDF58CF9916C8DD13

The Hard Part

We still have to figure out what cardrc4keyhalf and cardsnowiv are.

A Strong Start

What do we know? It is already known that these two variables can be switched between based off of the gamecard's ID1 and ID2. That's why the above image has commented out three sets of these variables (because there are four possible sets of ID1 and ID2). Since these variables are set when talking to the gamecard, it makes sense to start looking in the firmware files which perform this task. This is probably firm0.bin. I have disassembled a raw firm0 file using Reko, using both Thumb and Arm32 disassembly (since it is hard to know which is which in the file). Note that the vast majority of the firmware is written in Thumb, however. I have attached those disassemblies in the repository for those who are interested. I have already found a good anchoring point in the firmware, at address 0xC7708. This address contains half of a constant (0x71C93FE9BB0A3B18) which is sent to gamecards by the 3DS (the other half is at 0xC7710), which implies that the 3DS is using that region of code to talk to the card.

Simple Searching

We now need to do a simple search to find out when this constant is used. It can be seen that a few lines nearby, the following is found (I have added some comments):

What this does is to load the constant into address 0x10164008. Address 0x10164000 is the starting point for the NTRCARD registers, so the 3DS is sending the commands as if it were talking to a DS gamecard. Indeed, address 0x10164008 is used to send commands to the cartridge (see 3DBrew. What does it do then? Since the console does not yet know if the card is for the DS or 3DS, we should find where it determines this. When the 3DS sends the command 0x9000000000000000, it expects the card to respond with its ID1. We should therefore see where the next command is sent. Specifically, we want to know where the aforementioned one is sent, so that we can see when the NTRCARD FIFO is read, and what is done with this. This can be accomplished by searching for where the NTRCARD command register is written to. I was able to find some other locations, but the one which caught my eye was starting at 0xD14C2:

Let us take a look at what this actually does. A certain address is stored in sp. In 0xD14C2-8, the address pointed to by sp is cleared by zero-filling it, and then in 0xD14CA-E8, the value pointed to by register r0 is byte-swapped and then stored in the address pointed to by sp. In 0xD14EA-F2, the NTRCARD command register is filled with the value in the address pointed to by sp, and then in 0xD14F4, there is a funtion return. What this tells us is that this is a function which byte-swaps whatever is pointed to by r0, and then sends that to the gamecard as a command. If we can find where this is called, this will show us what commands are sent. We know this is a function also because right before this is a return statement, so it is impossible that there is any code which continues executing into this. There seems to be only one place which calls this function, which is at 0xCFEE8. This is as follows:

Remember that we are looking for the address loaded into r0 (not the actual value in the register, but rather the address it points to). What is this value? A simple analysis shows that r0 is equal to the stack pointer plus 8. This means that the value of interest is equal to the 8-12th byte of the stack, which should theoretically correspond to the third-to-last integer pushed there since the CPU is 32-bit (4 byte). Since this block of code is inaccessible without a branch, it must be called somewhere. Where? At 0xCFF40. This is not a call, however, but rather a branch. We need to dig deeper to find the underlying push to the stack. Going upstream, it can be found that this is located in a function starting at address 0xCFEE8, which is the one we just looked at. I suppose there is some kind of recursive function here that breaks at some point. But this is actually good, because it gives us a closed loop to look in. Looking here, I found something I did not notice before: That r0 loads up the third stak byte with a zero, but then passes that same byte into the command-sending function. This means that it is just sending out a zero, which is a real NTRCARD command. But I then realized a critical point: When calling our command sender, address 0xD14C0 is loaded, which is in the middle of an instruction. I assumed this was just garbage initially, but perhaps it is something else? Disassembling, I got: push {r2, r3, r4, lr}. Aha! This is the missing stack push. You should never put too much faith in your disassembler. But what does this mean for our work? These items are pushed to the stack, but in the following instructions, they are seemingly not used. In the above function. 0 is moved into r0, and then this value is effectively pushed to the stack. Then, r0 is set to the address of that item in the stack, and the command funtion is called. Let's look at this again.

The only possible way that the funtion can not always be sending a 0 command is if spo+8 was overwritten at some point. R0 is passed into the function pointing to a certain address, but that address need not be the original value present. The problem with this is that there is no intermediate point between where the address pointed to by r0 is set to 0, and where it is written as a command. It would make no sense that the command function would only ever have 0 passed into it, because it performs a byte swap. This implies that this function is intended to be used as one which is general-purpose. This function is only explicitly called once, at the address I showed before, so there must be something I am not taking into account. But then again, it seems to be impossible that this would do anything other than output a zero command. In our case, the if statement is false, so the next line calls FUN_000c9c44. After further analysis, it is simply impossible to get anything done without knowing what memory address contains what we want. We need to find where the encryption process occurs. It may be helpful to first look for where the titlekeys are derived. These use part of the header, so it makes sense that we should first look for where the header is used. That's where the 0x82 command is sent, but we don't know where that is yet since the CTRCARD CMD register seems to never be written to. But it does not make sense that Nintendo would implement a register without ever using it. The only possible reason for no being able to find where the register is written to (Address 0x10004020) is that our tools cannot find it. The most logical choice would be to find where the base address (0x10004000) is accessed, and then do some more analysis to find where this is offset and written to. Luckily enough, there are three addresses equal to 0x10004030. Remember that ARM32 cannot have 32-bit immediates, so it must store 32-bit address constants in a memory address, and then access them later. It turns out that whenever I searched for 0x10005030, all instances of 0x10004030 also came up, but they were misinterpreted as the former. I have no idea why this is, but I have now realized that this seems to be known in the 3DBrew documentation (it says CTRCARD registers are 0x10004000/0x10005000).
