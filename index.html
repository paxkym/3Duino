The encryption problem

I will not go into excessive detail about the known parts of the 3DS gamecard protocol, since it can be found everywhere online and I don't want to clutter this article. The gist is that there is a bunch of unencrypted data sent to the 3DS by the gamecard when it is first plugged in, followed by encrypted data. The encrypted data is encrypted using a known set of algorithms, which take into account both data from the unencrypted section of the card, as well as some secret information in the 3DS itself. The hard part of all of this is figuring out what that secret info actually is.

Protocol info

Before any actual decryption work is done, we must first establish the actual protocol used. There are 2 encryption methods used: SNOW 2.0, and RC4. The exact details of these will be explained later. Anyway, the SNOW (I will use the term 'SNOW', even though this is actually SNOW 2.0, which is different from the original SNOW) cipher is used to generate a key for the RC4 cipher, which then does the actual encryption. SNOW takes in a key, as well as an initialization vector. From there, you can encrypt as many words (sets of 4 bytes) as you wish. RC4 takes in one key, and also produces a stream in a similar manner. Let us create a chart to help remember this:
Initialization inputs Cipher input length Cipher output length
SNOW 2.0 Key (16 bytes), Initialization vectors (16 bytes) 4 bytes 4 bytes
RC4 Key (16 bytes) 8 bytes 8 bytes
Let us also make note of all of the unknown variables present:
Name Nickname Size
Title key 1 TK1 4 bytes
Title key 2 TK2 4 bytes
SNOW2.0 initialization vectors SNIV 8 bytes
RC4 key half RCKH 8 bytes

While I could theoretically just try and reverse the RC4 encryption algorithm or restore the image that I showed before, the reality is that even if you knew all of the unknown variables for this one particular gamecard that we are looking at, those variables change based off of the card. In other words, the image of card decryption that I just showed above is not a universal algorithm. It only works for one particular card (Lego starwars 3). The way that these variables are derived in the first place is from the gamecard header information, by the 3DS's firmware, so the unknown in this case is not a simple set of numbers, but rather a derivation algorithm. The goal of this project is therefore to create a program which can, using the header, decrypt those commands we saw before. Our work is cut out for us now.
