Deciphering the 3DS gamecard protocol

My 3DS joystick broke. I wanted initially to repair it, whick worked, but then other problems got in the way, and eventually it became unusable. I decided that perhaps I could play my 3DS games without a physical console, but instead with an emulator. To do this, I would need to obtain information from my gamecards. I also thought it would be a fun project to practice my bit-banging skills. So, without further ado, here is sufficient information to read 3DS gamecards yourself! To perform this task, the pinout of the device must be established. This can be found from numerous sites, but I will use an adaptation from 3DBrew:

  • Pin 1: Ground
  • Pin 2: Clock
  • Pin 3: Ground
  • Pin 4: ROM select/RCS (active low)
  • Pin 5: Reset (active low)
  • Pin 6: Save select/ECS (active low)
  • Pin 7: Ground
  • Pin 8: 3.3 volts
  • Pin 9: D0
  • Pin 10: D1
  • Pin 11: D2
  • Pin 12: D3
  • Pin 13: D4
  • Pin 14: D5
  • Pin 15: D6/CIPO
  • Pin 16: D7/COPI
  • Pin 17: Ground
Note that the pins are numbered from left to right, from the perspective of the back of the card where the gold pins are when the card is upright.

Reading save data

It appears as though save data is much easier to read than the actual ROM. This is because the chip which stores the save information is well-documented and can be bought online (datasheet here) To read save data, pin 6, heretofore referred to as ECS, is pulled low. Then, the 3DS will send a command asking for data, and then the cart will respond with save information. According to 3DBrew, data pins D4 through D7 are the pins used to transmit save data. According to problemkaputt, only D6 and D7 are used. However, upon checking the datasheet, the latter is correct. To test these conflicting ideas, I hooked an Arduino up to a gamecard, set ECS to low, and sent the following commands: 0x03 0x00 0x00 0x00 The commands were sent serially, so each bit was sent through pin D7, since this is the COPI pin. Every other pin was kept at 0. Then, I ran the clock, and, sure enough, save information was sent through pin D6 (because that is the CIPO pin). That wraps up the save data.

Reading ROM data

Please read this article first. It gives many prerequisites to understanding the following. To read the unencrypted section of the gamecard, the command: 0x9000000000000000 must be sent (supposedly). I tried sending all of the commands necessary according to 3DBrew using all 8 data pins, but never got any response data. This made me suspect that perhaps the protocol listed was simply not correct. I decided to probe the communication between the 3DS and gamecard to find out what was actually going on. Upon starting the console, the following command was sent:

00 00 00 00 70 70 00 00 00 20 00 E0 00 00 00 F0 E0 E0 00 00 00 F0 30 70 00 00 00 F0 00 70 00 00 00 F0 00 70 00 00 00 B0 00 70 00 00 00 A0 00 70 00 00 00 00 00 00 80 00 70 00 00 00 80 80 F0 00 00 00 A0 80 70 00 00 00 80 80 00

A few observations are notable. First, none of the commands from 3DBrew are present. Second, data bits D4 through D7 are never used. This may be why it states that all of these bits are part of the save data protocol. Perhaps we can send this to the 3DS, and see the response.
