Deciphering the 3DS gamecard protocol

Introduction

My 3DS joystick broke. I wanted initially to repair it, which worked, but then other problems got in the way, and eventually it became unusable. Instead, I have decided to make a program which reads data from the cartridge directly and outputs it for use by an emulator. One would think that this is a simple task, but it actually is not. The useless brats at Nintendo refuse to publish any information online about the console hardware, and all of the guides that I found online (3dbrew, for example) publish total garbage information about this protocol. When I tried to get the ROM protocol working as listed in the wiki, absolutely nothing worked. But, as the saying goes, 'If you want something done right, do it yourself'. Therefore, I have here shown the reverse engineered protocol as per my own experiments. Also, don't use this for piracy (wink wink), devaluation, crap romhacks, yadda yadda yadda. Enjoy! And please don't put this all on ChatGPT (not wink wink, actually serious). I put hard work into making this, and for some stupid robot to come and make money for Sam Altman off of my back is totally unnacceptable.

To perform this task, the pinout of the device must be established. This can be found from numerous sites, but I will use an adaptation from 3DBrew:

  • Pin 1: Ground
  • Pin 2: Clock
  • Pin 3: Ground
  • Pin 4: ROM select/RCS (active low)
  • Pin 5: Reset (active low)
  • Pin 6: Save select/ECS (active low)
  • Pin 7: Ground
  • Pin 8: 3.3 volts
  • Pin 9: D0
  • Pin 10: D1
  • Pin 11: D2
  • Pin 12: D3
  • Pin 13: D4
  • Pin 14: D5
  • Pin 15: D6/CIPO
  • Pin 16: D7/COPI
  • Pin 17: Ground
Note that the pins are numbered from left to right, from the perspective of the back of the card where the gold pins are when the card is upright. Also note that all data on here is represented in hexadecimal, but will not have the conventional 0x marker at the beginning, since this makes it harder to read.

Reading save data

It appears as though save data is much easier to read than the actual ROM. This is because the chip which stores the save information is well-documented and can be bought online (datasheet here) To read save data, pin 6, heretofore referred to as ECS, is pulled low. Then, the 3DS will send a command asking for data, and then the cart will respond with save information. According to 3DBrew, data pins D4 through D7 are the pins used to transmit save data. According to problemkaputt, only D6 and D7 are used. However, upon checking the datasheet, the latter is correct. To test these conflicting ideas, I hooked an Arduino up to a gamecard, set ECS to low, and sent the following commands (hexadecimal):

00 00 00 00 00 00 01 01

00 00 00 00 00 00 00 00

00 00 00 00 00 00 00 00

00 00 00 00 00 00 00 00

The commands were sent serially, so each bit was sent through pin D7, since this is the COPI pin. Every other pin was kept at 0. Then, I ran the clock, and, sure enough, save information was sent through pin D6 (because that is the CIPO pin). However, this is not the case for all gamecards. In fact, I only had one card for which this worked. This is because the majority of 3DS gamecards actually use a different savedata chip: the MX25L40 (technically the 4001, specifically, but the 4005 listed here is close enough). This uses a slightly different protocol. That wraps up the save data.

Reading ROM data

When I tried using the protocol usually listed online for reading ROM data, I first concluded that this protocol was simply incorrect. However, upon further anaylsis, it in fact is correct, and it is just very difficult to get a good enough connection.

Blowfish Encryption

The DS uses an encryption algorithm for some of its commands called 'Blowfish'. This algorithm will now be explained.

Overview

This algorithm has a key, which is used for both encryption and decryption. This key can be anywhere between 5-46 bytes long. Data is encrypted in 'blocks' of 8 bytes each, where the plaintext and ciphertext are both 8 bytes long.

Variables

There are a few variables to have known. Even though some of these have already been mentioned, it is good to go over them again.

    Key: 8-46 bytes long, used for encryption and decryption
    Plaintext: 8 sets of 1 byte (uint8_t)
    Ciphertext: 8 sets of 1 byte (uint8_t)
    P-array: 18 sets of 4 bytes (uint32_t [18])
    S-boxes: 4 sets of 32 bytes (uint8_t [32][4]
