The encryption problem

I will not go into excessive detail about the known parts of the 3DS gamecard protocol, since it can be found everywhere online and I don't want to clutter this article. The gist is that there is a bunch of unencrypted data sent to the 3DS by the gamecard when it is first plugged in, followed by encrypted data. The encrypted data is encrypted using a known set of algorithms, which take into account both data from the unencrypted section of the card, as well as some secret information in the 3DS itself. The hard part of all of this is figuring out what that secret info actually is.

Protocol info

Before any actual decryption work is done, we must first establish the actual protocol used. There are 2 encryption methods used: SNOW 2.0, and RC4. The exact details of these will be explained later. Anyway, the SNOW (I will use the term 'SNOW', even though this is actually SNOW 2.0, which is different from the original SNOW) cipher is used to generate a key for the RC4 cipher, which then does the actual encryption. SNOW takes in a key, as well as an initialization vector. From there, you can encrypt as many words (sets of 4 bytes) as you wish. RC4 takes in one key, and also produces a stream in a similar manner. Let us create a chart to help remember this:
Initialization inputs Cipher input length Cipher output length
SNOW 2.0 Key (16 bytes), Initialization vectors (16 bytes) 4 bytes 4 bytes
RC4 Key (16 bytes) 8 bytes 8 bytes
Let us also make note of all of the secret variables present:
Name Nickname Size
Title key 1 TK1 4 bytes
Title key 2 TK2 4 bytes
SNOW2.0 initialization vectors SNIV 8 bytes
RC4 key half RCKH 8 bytes

While I could theoretically just try and reverse the RC4 encryption algorithm or restore the image that I showed before, the reality is that even if you knew all of the secret variables for this one particular gamecard that we are looking at, those variables change based off of the card. In other words, the image of card decryption that I just showed above is not a universal algorithm. It only works for one particular card (Lego starwars 3). The way that these variables are derived in the first place is from the gamecard header information, by the 3DS's firmware, so the unknown in this case is not a simple set of numbers, but rather a derivation algorithm. The goal of this project is therefore to create a program which can, using the header, decrypt those commands we saw before. Our work is cut out for us now.

The beginning of derivation

Where exactly do these variables come from? Let us figure this out (all information comes from 3DBrew):

TK1 and TK2

These two variables are actually just the left and right halves, respectively, of a single output from the SNOW cipher. Call this TK1-2. TK1-2 is, in turn, the output of an 16-byte CCM mode AES cipher. This cipher contains a 32-byte key, and a 12-byte nonce. TK1-2 is derived in the following way: Combine header bytes 0x00-0x10, with a secret number hidden in the 3DS's boot firmware, and make these a new key. Set the nonce to header bytes 0x30-0x3c, ad then decrypt header values 0x10-0x20 using the key we established before. This output is TK1-2. This brings into play a new secret variable: KeyX, as well as the algorithm for combining the first 16 header bytes (KeyY) with KeyX to generate what is known as the NormalKey (NK). Call this algorithm algo1. While we do technically have enough information to determine the output that algo1 would produce exclusively from the header, it would take an average of 2^127 iterations, which is impractical. Remember that AES encryption is very secure.

3DS AES crash course

The 3DS encrypts a bunch of things using the AES cipher. Since there is so much encryption to be done on the 3DS, there is a dedicated part of the 3DS's CPU just for AES. This can be interacted with using what are known as the AES registers. Recall that the 3DS is a 32-bit system, so each register holds 4 bytes. The AES hardware is able to perform multiple (about 20-30) different encryption processes in parallel, so the AES hardware is divided into a number of "keyslots". These keyslots all contain a normalkey, a KeyX, and a KeyY. They are controlled by a set of AES registers, the most important of which are the following:
AES_CNT [4] (Read/Write) Sets a number of settings
AES_WRFIFO [4] (Write) Plaintext to be encrypted
AES_RDFIFO [4] (Read) Encrypted ciphertext
AES_KEYCNT [1] (Write) Selects the desired keyslot
AES_KEYYFIFO [4] (Write) Sets the KeyY
AES_KEYXFIFO [4] (Write) Sets the KeyX
AES_KEYFIFO [4] (Write) Sets the NormalKey

To use this mechanism, you must write to AES_KEYCNT which keyslot you would like to update, and then write to the last 3 registers mentioned what you would like to set the key values to. Afterwards, AES_WRFIFO and RDFIFO can be used for decryption. Remember that the KeyX, KeyY, and NormalKey are all 16 bytes long, so it will take 4 clock cycles to write the whole of the keys to the registers. To be honest, I am actually not sure whether this mechanism encrypts or decrypts. This will probably not be important though, as long as we can figure out where the keys come from. For the purpose of gamecard decryption, the only important AES register is 0x3B. This is the register where KeyX is written, which we can thus trace to discover how the 3DS determines its value.

Down the bootloader rabbit hole

Ok, so back to the bootloader now. We need to first find out what happens when the CPU contacts the AES registers. It seems as though these registers are just RAM addresses, so maybe we can search for mentions of them? The most important, AES_KEYXFIFO, has an address of 0x10009104. Searching for this yields nothing. However, searching just for 0x9104 yields extraordinary results. This is where the article starts to get a bit cluttered, but please bear with me.
